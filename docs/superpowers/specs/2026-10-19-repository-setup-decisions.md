## Research and design implications

- **Projects credentials:** repository `GITHUB_TOKEN` cannot access Projects. GitHub recommends a PAT for user-owned Projects; its Actions example uses classic `project` and `repo` scopes. This is a separate credential decision from local setup authentication. [Projects Actions authentication](https://docs.github.com/en/issues/planning-and-tracking-with-projects/automating-your-project/automating-projects-using-actions). The CLI requires `project` scope and documents `gh auth refresh -s project`. [CLI Projects](https://cli.github.com/manual/gh_project).
- **Native Projects automation:** auto-add limits are one workflow on Free and five on Pro. Enabling auto-add does not backfill existing matching items. A one-repository native rule may suffice for basic intake; advanced transitions need their own design. [Auto-add](https://docs.github.com/en/issues/planning-and-tracking-with-projects/automating-your-project/adding-items-automatically).
- **Git Flow and Issues:** PR closing keywords are interpreted only for PRs targeting the default branch. Feature PRs into `develop` therefore need deliberate linking and completion handling when `main` is default. Manual linking and explicit references can preserve traceability. Implement the selected child-PR completion lifecycle explicitly rather than relying on default-branch closing keywords; closed-unmerged exceptions pause affected completion/release readiness for manual chat resolution. [Issue linking](https://docs.github.com/en/issues/tracking-your-work-with-issues/using-issues/linking-a-pull-request-to-an-issue).
- **Draft lifecycle:** draft PRs cannot merge. Marking ready requests code-owner reviews where configured. Proposed triggers should distinguish opened draft, ready, updated ready, returned-to-draft, merged, and closed-unmerged.
