## Behavior

`project-sync.yml` runs trusted default-branch `native-project-sync.mjs` on Issue metadata changes, develop-targeted PR metadata changes and completed `Ready CI` runs. It refreshes native Development links, sub-issues, parents and blocking dependencies from GitHub, including closed PRs through `closedByPullRequestsReferences(includeClosedPrs:true)`. Body links and labels do not invent delivery scope. Existing native intake rules remain responsible for adding Issues and setting Backlog; a missing Project item is an error, not a second intake mechanism.

No linked work leaves Backlog/Planned unchanged. Draft or active delivery work selects In progress. In review requires all active mapped PRs Ready with a successful latest applicable Ready CI run for the **current PR head**, and a fresh native comparison proving that exact tested head includes **current develop**. The run is independently fetched, including its current attempt; immutable `run.head_sha`, repository/workflow/path/event and native PR association membership identify applicable CI. Association `pull_requests[].base/head` objects are live metadata and are not historical run-time base/head evidence. The comparison uses exact develop/head commit IDs, accepts ahead/identical ancestry, validates native base/merge-base and final chronological head identities, and rejects diverged/behind or incomplete results. CI from another workflow/repository, an earlier tested head, pending rerun or newer failed/cancelled run cannot qualify. This establishes current-base inclusion in the tested head, not an event-time base/head pair; independent code review still binds the exact current pair before merge. An aggregate with unfinished children remains In progress unless every unfinished child is In review and it has qualifying own active PR work.

Integrated requires every mapped delivery PR merged into develop, every native child and blocking dependency independently valid and closed completed, and the Issue's own acceptance checklist checked. A pure aggregate can complete without an own PR. Checklists count only in explicit `Acceptance`, `Acceptance criteria` or `Approved scope` Markdown sections, outside fenced examples. Unordered and ordered task markers are supported, and closing code fences must match the opening character with at least its delimiter length. At least one checkbox is required; unsupported prose-only acceptance requires chat reconciliation. Checking a box is a native maintainer assertion, not proof that tests ran. Historical offline engines remain preserved and are not used to manufacture richer provenance guarantees.

Only Status changes, then eligible open Issues close with `state_reason: completed`. Fresh repeated native source reads precede each write; independent reads verify both Status and closure. Milestones, labels, relationships, dependencies, priorities, sizes and bodies are never edited. Closed not-planned/duplicate Issues are not delivery and are never reopened. Closed-unmerged or differently targeted delivery PRs block completion pending chat reconciliation. Cancelled/deferred children remain in scope and block their parent; only the product owner can decide scope reduction or deferral, recorded through the established chat process. Released Status is always preserved; it does not replace missing integration evidence in a parent's gate. This adapter cannot set Released or invent publication evidence. Verified release automation awaits actual product build/assets.

## Credential setup

Source delivery does not provision credentials. Root will request actual access after reviewed setup is concrete. The postponed reviewer identity/App decision is separate.

Repository `GITHUB_TOKEN` permissions are exactly `contents: read` (trusted checkout), `actions: read` (Ready CI), `pull-requests: read` (relationships/current PR), and `issues: write` (metadata reads and eligible Issue closure). All other permissions are none. The repository token cannot mutate this personal Project.

For this personal Project2 GraphQL adapter, an owner-approved **classic personal access token with only `project` scope** is the supported interface. `read:project` cannot write; `repo`, `workflow`, admin and other scopes are unnecessary for this public repository. The `project` scope includes project read access and is account-wide: classic PATs cannot restrict it to only Project2. Choose a short expiration, retain owner control and rotate/revoke through GitHub. Do not substitute an organization Projects fine-grained grant for a personal Project without separately validating support. See [GitHub's Projects API authentication](https://docs.github.com/en/issues/planning-and-tracking-with-projects/automating-your-project/using-the-api-to-manage-projects) and [personal versus organization Projects API token support](https://docs.github.com/en/rest/projects/projects).

After owner authorization, save that token as the **repository Actions secret `PROJECTS_TOKEN`** in this repository's Settings → Secrets and variables → Actions. Do not add it to a checkout, `.env`, workflow input, issue, log or agent context. The runner receives it only in its trusted execution step; only Project-item queries and the Status mutation use it. Repository reads and Issue closure use `GITHUB_TOKEN`. Checkout has credential persistence disabled. No dependency installation or candidate checkout/execution occurs in this privileged job. Missing either credential is an explicit failed/blocked run, never successful pretend synchronization.

## Delivery and verification

Land reviewed source into the actual default branch before relying on these events. The workflow uses the GitHub-provided default-branch SHA for these metadata events; it does not execute PR scripts. Reuse the reviewed pinned checkout/setup-node actions and Node24.19.0. The runner uses Node built-ins and needs no npm installation. New source formatting participates in `npm run format:check`; meaningful adapter/transport tests run under `npm run test:governance` and the existing full local gate.

Hosted acceptance is still pending: authorize/provide Project access, verify workflow availability on the default branch, then observe actual Draft→In progress, Ready+current successful CI→In review, failed/stale CI→In progress, partial multi-PR merge staying open, all-PR/child/acceptance completion→Integrated and completed closure, plus Released preservation. Independently read back native IDs, Status, closure and untouched scope fields. Do not describe local fake-transport tests as live Project verification. Existing ordinary Actions availability does not prove this workflow's delivery/access/acceptance.

## Manual reconciliation and limits

Any failed/uncertain API response or mutation/readback stops the job without automatic retry. Logs name the Issue and reconciliation reason where available. Review the live Issue, its native links/parents/dependencies, Project item and run results before deciding the next action; do not blindly rerun an uncertain write. A successful Status write followed by failed closure can leave Integrated/open; reconcile and deliberately rerun only after reading current native evidence. Required missing acceptance or exceptional delivery evidence stays open and logs reconciliation; no Issue comment/message is automatically posted.

`native-project-sync` concurrency serializes participating jobs, with `cancel-in-progress: false`. GitHub can replace pending runs and delivers events asynchronously; this is not an event journal. A later event refreshes current native state rather than replaying stale payload decisions. Direct native edits, other workflows, ready/draft controls and humans remain concurrent. Reads and Status/closure writes are non-transactional; repeated fresh comparisons reduce races but cannot eliminate changes after the last read or prove ordering inside GitHub timestamp precision. There is no distributed fence or shared backend.

Traversal is limited to 100 Issues per affected snapshot, depth 19, 10 pages/1,000 nodes per relationship or CI listing, at most 1,000 ahead commits for native comparison (only the final chronological page is needed to verify the head identity), 3,000 API requests per job, 20-second requests, 4 MB JSON responses and a 15-minute job. Null nodes, duplicate IDs, changed totals/cursors, unsupported/missing data, inconsistent parents, cycles or foreign-repository relationships fail closed. Sibling Issues are read to assess a parent, but only event-linked Issues and their current ancestors are mutation targets. Dependencies are read, never rewritten or auto-closed by association.

There is no polling or mass sweep. Native relationship-only changes, project field changes and advancing develop may not emit a selected event for every affected Issue. Refresh on a subsequent participating metadata event (for example a deliberate Issue body update after reconciliation). Removed PR links or reparenting can hide the former target from a current-only event; reconcile that former Issue/parent explicitly. Empty fork workflow-run PR associations also require reconciliation. A missing Ready CI workflow returns an explicit API failure until its separate reviewed source is delivered. These practical limits do not claim universal provenance, atomicity or automatic recovery.
