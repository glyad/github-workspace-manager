## Install and checkpoints

Use the pinned Node/npm runtime and `npm ci`. In each checkout run `npm run governance:install-hooks`. Installation enables Git's worktree config and writes/reads back `core.hooksPath=.githooks` for that checkout. Linked worktrees need their own installation; keep their branches separate. These files do not claim installation on an existing checkout.

Create ordinary work with `npm run governance:new-work -- feature/ISSUE-description`. The command fetches the actual `develop` parent, creates the branch from that fetched commit and returns the starting SHA. It does not create a PR. Existing branches use the actual PR base and the explicit `branch.BRANCH.governance-parent` setting (default `develop`); a mismatch blocks work. The guard verifies the approved origin, repository identity, same-repository PR head and open state through existing `gh` authentication. Read failures stop work.

Before editing, run `npm run governance:pre-edit -- CHECKPOINT`. Checkpoints are `identify-parent`, `new-work`, `before-change`, `resume`, `parallel`, `interface-change`, `final-validation`, `review-fix`, `pre-integration`, `downstream-merge`, `preserve-work`, `literal-merge`, `push-sync`, and `invalidate-evidence`. They share the approved fetch/merge discipline at explicit work boundaries. A Ready or reviewed PR must first become remotely verified Draft, including before parent merges. A branch without a PR still requires verified PR absence, branch/parent checks and configured checks on commit/push. If a PR appears while checking, refresh context and retry.

Ordinary `feature/`, `chore/`, `doc/`, and `fix/` work targets `develop`. `hotfix/` integration requires the explicit `branch.BRANCH.governance-phase=hotfix-integration` setting and the same develop guards. This command does not execute `hotfix-shipping` or `normal-release` transactions. The later release orchestrator owns released-tag provenance, shipping without develop and the authorized direct develop-to-main release exception. That exception remains authorized; it is unsupported by these ordinary-work commands.

## Local checks and evidence

`governance/checks.json` runs the real governance tests, ESLint, Prettier checks and public-file policy checks. No product check is declared before product implementation exists. Every commit attempt and changed downstream merge runs checks, including Draft work. The pre-commit guard exports the actual index to an isolated temporary snapshot; dirty working files are retained. It rechecks the index tree after checks and remote Draft verification. Unmerged entries fail closed. Checks run without Git's hook environment, so test repositories cannot inherit the caller's index. Configured dependencies are shared through the existing ignored `node_modules` directory; no new dependencies are installed by a hook.

Pre-push reads every ref/SHA on stdin. The actual hook destination and every effective origin fetch/push URL must identify the approved repository; an unrelated extra push URL blocks the entire operation before the first push. Each same-name ordinary branch is independently observed, checked against its local SHA and destination old SHA, verified Draft (or verified PR absence), and tested from the exact proposed commit tree. Deletions, renamed refs, tags, unsupported main/develop transactions and non-fast-forward updates are blocked here. The guard has no general skip flag and never runs a nested commit/push, preventing recursive hook invocation.

Synchronization uses literal `git merge --no-ff --no-commit` of the fetched parent SHA. It runs local checks, rechecks the live parent, creates a signed commit with `-S`, verifies its signature and immediately pushes without force, then reads back the remote branch SHA. The producer uses a same-name branch refspec and pins its expected ref/SHA for the installed hook; the hook rejects a changed candidate and still rejects raw-SHA source refspecs. These scoped identity variables are removed from check subprocesses and grant no check bypass. If already an ancestor, it records that fact without manufacturing a merge commit. Returned evidence pins the observed parent and before/after head; it always leaves readiness false and invalidates previous review. Human merge approval and fresh CI/independent review are separate later gates. A parent-only change also invalidates earlier evidence.

## Recovery and limits

Dirty/untracked work blocks synchronization before a merge begins. Preserve it in its existing checkout or use an isolated checkout; the guard never stashes, resets or discards files. Conflicts leave `MERGE_HEAD` and conflict files available. Resolve without discarding unrelated work, obtain any needed product decision, run the configured checks, create a signed merge commit and immediately push while verified Draft. A failed check, signature, push or remote read-back blocks readiness/integration. A failed push can leave a valid local merge commit: retry a normal guarded push, read back its SHA and repeat current-parent validation and exact-candidate review. Do not amend/rebase/force-push the published identity to repair uncertainty.

Hooks and pre-edit commands are local cooperative enforcement. Git clients can omit hooks or use their own Git/config/runtime; editing cannot be intercepted by Git. Run the pre-edit command explicitly, verify hook installation in every checkout and retain the remote readiness safety net before enabling hosted automation. GitHub's Draft mutation has no compare-and-swap: the guard checks immediately before mutation and reads back the complete base/head identity afterward, blocking on drift. A concurrent remote change after the final observation remains possible; remote admission and final integration reconciliation must reject stale evidence. These local commands never mark Ready or authorize integration.

## Remote readiness admission

Task 6 is a staging implementation. Actions execution and the controller remain inactive; integration remains blocked. The accepted Task 5 local guards remain a separate change. No hosted CI or paid review is started by this implementation. See the [activation gates](activation-runbook.md).

Every expensive worker must call `admitCandidate(port, event)` immediately before starting and on consequential completion. All callers share `repositoryId:pr` serialization, including controller events and worker completions. `decideReadiness` is pure policy; `reconcileTransition` is a trusted, lock-held internal transition function. Do not expose decisions or trusted observation fields to PR-controlled callers. The live serialization adapter is unresolved. Actions concurrency alone can replace pending jobs and is insufficient as a durable queue; reread latest native history, current PR/base/head and authenticated journal instead of assuming event order or cancellation success.

A protocol-v2 candidate is exactly `{repositoryId,pr,base,head,attempt,baseRef,requestId,protocolVersion:2}`. `attempt` remains the native Ready event ID; a workflow run ID never substitutes for it. The accepted durable operation, authenticated original request and retained complete proof/window establish admission-time identity. Current native history must retain that complete accepted prefix, show the same latest Ready witness and exact current pair/ref, and exclude intervening lifecycle or detected candidate changes. Legacy candidates remain parseable only for historical reconciliation.

Every start and consequential completion repeats the full native/proof/journal check under the same PR lock. Current Draft/closed state, missing or incomplete history, closure/reopen since admission, detected base/head/ref drift, unresolved intent/quarantine or missing proof denies work. Record authenticated drift as attempt-scoped invalidation; restoring an earlier pair cannot revive it. A delayed event for an earlier Ready ID cannot invalidate or draft a newer attempt. A matching current head-change safety event may return the exact current attempt to Draft after revalidation; it never creates another CI cycle.

Journal intent and result need independent exact-byte/run-authenticated append/readback with immutable membership. An unknown write/mutation/consumption outcome remains pending and grants no work. A later verified readback can reconcile actual persisted history; missing ledger rows after an outage are not fresh eligibility. Pending obligations retain exclusion across restart. Status writes recheck the exact current candidate immediately before and after mutation; any detected race quarantines and requires reconciliation. No automatic Ready restoration exists. Before/after reads cannot prove event-time SHAs, uninterrupted equality, unique causality or readiness CAS; an unobserved transient change may evade them. Completion grants no merge authority; `glyad` remains sole merger.

## Verified readiness command

The [owner-approved admission amendment](../superpowers/specs/2026-10-22-verified-admission-design.md) and [plan](../superpowers/plans/2026-10-22-verified-admission.md) govern the dormant command. On a deliberate human request, provide exactly six dispatch strings: `pr`, `expected_base_ref` (`refs/heads/...`), lowercase 40-hex `expected_base_sha`/`expected_head_sha`, unique ASCII `request_id` (1–128 alphanumeric/underscore/hyphen), and `protocol_version` exactly `2`. Expected values are assertions to verify; never replace them with a fresh PR read. The controller resolves trusted repository/node/actor/original-run/definition identities independently. Input strings travel as JSON in environment data and never enter shell source.

Success says “Ready and admitted for these commits”. All denied, uncertain or conflicting results say “Not admitted; reconciliation required”. The first increment supplies a workflow-dispatch recipe and injected runtime boundary; no separate command wrapper or production provider is selected. An original allowlisted human starts the request; reruns retain that original actor, exact request bytes and approved default-branch definition. Changed dispatch inputs, triggering actor, branch definition or run attempt attribution deny. The automation actor is recorded separately from the initiating human.

A native **Ready for review** button click alone never admits CI. A shared bot producing a plausible Ready event outside the registered controller path also grants no authority. Register and authenticate every readiness writer, controller path and journal/proof issuer before activation; a bot name match or native timestamp is insufficient. The shared writer inventory and numeric actor allowlist are production capabilities still unselected, not implicit grants.

On an unknown outcome, preserve the operation/claim and reconcile authenticated original evidence. Discovery binds only the original CI run, never another run or rerun. Resolve the previous obligation, deliberately return the PR to Draft as a human, verify that state, then issue a new request for the intended pair. Do not delete locks, erase history, retry a mutation/send blindly or automatically restore Ready. The local test store has no dead-holder takeover; a killed holder retains its lock and excludes work until separately authenticated recovery is possible.

A claim-bound authenticated start must newly consume permission before it checks out exact admitted base/head values and runs the real `npm run check:local` recipe. It has both a false job gate and an unconditional failing activation preflight. Runtime checkout/import is deliberately absent until a separately reviewed external bootstrap/protected configuration authenticates approved immutable default-branch source before code load. A dispatch-selected `github.workflow_sha`/ref or environment assertion is not independent source authority. The privileged controller never checks out or executes PR code/configuration. The local offline composition routes CI start/completion through D with the original durable claim identity; a future independently trusted host must supply that boundary before the nonexecutable workflow recipe can run; only newly consumed start permission reaches candidate checkout/checks. Reruns and duplicate starts deny execution. The offline admission/claim bridge is implemented; no live providers, candidate-bound production result issuer or code scanner is selected; it emits no governance success. Real product tests and a verified scanner must be added once available rather than replacing them with no-op successes.

Admission must bind the trusted workflow definition revision separately from untrusted candidate revisions. Never use a synthetic PR/develop merge ref. Shipping hotfix validation uses its frozen shipping head and latest released same-line baseline, with no develop merge before publication. Later develop integration is a separate admitted candidate after synchronization; it preserves the published tag/artifacts. This staging policy does not implement the release orchestrator or prove same-line tag provenance.

The inactive review recipe fixes fresh `gpt-6-astra`/High and isolates the planned posting job. It wires no key and cannot run. Read the [worker activation gates](activation-runbook.md#isolated-workers-and-review-activation) before any change. Treat every PR-controlled byte as data, including filenames, diffs, comments and instructions. A trusted runner must validate and measure the exact complete input, exclude candidate configuration and executable paths, reserve/claim a single-use funded slot and recheck admission immediately before analysis and on completion. Workflow concurrency is not the durable reservation lock. Completion never grants merge authority; glyad remains sole approver.
